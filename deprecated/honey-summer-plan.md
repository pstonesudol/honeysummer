## 4. Key Flow: No-Oversell Inventory

1. Florist (or retail customer) submits checkout → Sanic creates **pending Order** and decrements `quantity_available` inside a Postgres transaction with row locks (`SELECT … FOR UPDATE`); rejects cleanly with "insufficient quantity" if stock ran out.
2. Create Stripe Checkout session (line items + delivery fee) → redirect.
3. A signed payment event must match the saved session, USD currency and exact snapshotted total, and prove payment before conversion to **paid**. Async/delayed payments remain pending until verified success/failure. Queue customer/farm confirmations in the retryable outbox; provider acceptance is not proof of inbox delivery.
4. Confirmed expiry/async failure releases an unpaid hold once; safe cancellation first verifies that Stripe can no longer take payment. Reconciliation recovers missed events/failed notifications without blindly releasing uncertain holds.
5. Paid orders progress through fulfillment, not cancellation/hold release. Refund journals and explicit returned-stock adjustments are separate; a refund never automatically restocks. Bouquet/wedding invoices use separate payment identities and do not reserve seasonal stock merely by sending a quote.

## 5. Auth Architecture

- Sanic session auth with opaque HTTP-only cookies backed by hashed Postgres session records and per-user revocation versions (Phase 11 replaces the earlier signed user-ID cookies). - Wholesale pages server-check session + `approved` flag; unauthenticated → login; unapproved → "pending approval" page.
- Wholesale shop signup is the **only** wholesale access-request path: it creates an unapproved florist account with the applicant's business details and self-chosen password, then emails Isabella; she reviews the details in admin and approves it → approval email with login link. The former duplicate wholesale inquiry form is removed; pre-signup questions link to the Contact form (reason: Wholesale).
- Phase 11 implements admin/staff permissions, revocable sessions, password/invite/email recovery, optional MFA for admins, staff and florists, API CSRF/Origin hardening, atomic IP/account rate limits, notifications, security auditing and admin recovery procedures. Password-only sign-in is allowed when no authenticator is enrolled; enrolled MFA remains required at sign-in and sensitive reauthentication.
